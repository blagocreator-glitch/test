# Аудит сайта «Ваши мастера» — отчёт о слабых сторонах

**Дата аудита:** 2026-06-02
**Объект:** статический сайт-витрина ремонта квартир (`index.html`) + калькулятор сметы (`smeta-pro.html`) + PHP-обработчик заявок (`send-mail.php`).
**Issue:** [#1 «Аудит сайта»](https://github.com/blagocreator-glitch/test/issues/1) — «Нужно провести аудит сайта и предоставить отчёт. Выявить слабые стороны.»

> Это отчёт-ревизия. Он фиксирует найденные слабые стороны с доказательствами (`файл:строка`), оценкой риска и рекомендациями. Сам отчёт ничего не ломает и не меняет в работе сайта; правки выносятся отдельными задачами.

---

## 1. Методология

Проверка проводилась по исходному коду репозитория без доступа к рабочему серверу. Охвачены направления:

- **Безопасность** (PHP-бэкенд, заголовки, конфигурация).
- **Приватность / утечки данных** (что попало в репозиторий).
- **Производительность** (вес ресурсов, отдаваемых браузеру).
- **Гигиена репозитория** (мусор, дубликаты, размер).
- **SEO и целостность ссылок** (мета-теги и реально существующие файлы).
- **Доступность (a11y)**.
- **Архитектура и сопровождаемость**.

Часть рисков уже зафиксирована в существующем `SECURITY_AUDIT.md`; данный отчёт его дополняет и проверяет, реализованы ли заявленные там меры.

## 3. Детальные находки

### 🔴 F1. Утечка персональных данных в `mail_debug.log`

Файл `mail_debug.log` (≈57 КБ) **закоммичен в git** и содержит реальные (или похожие на реальные) данные заявок:

```
{"name":"Дмитрий","phone":"+7 (985) 123-45-77","service":"Косметический ремонт","comment":"тест88","date":"21.03.2026, 16:03"}
    [phone] => +7 (985) 123-45-77
```

В логе ~48 строк с телефонами/именами/IP. Это **утечка персональных данных** (нарушение 152-ФЗ «О персональных данных»): любой, у кого есть доступ к репозиторию или к публичной выгрузке, видит контакты клиентов. Даже после удаления файла данные останутся в истории git.

**Риск:** компрометация ПДн, репутационные и юридические последствия.

**Рекомендации:**
1. Удалить `mail_debug.log` из репозитория и **переписать историю git** (`git filter-repo`/BFG) либо ротировать репозиторий.
2. Логи не должны лежать в веб-корне; директорию `logs/` вынести за пределы публичного доступа.
3. В `send-mail.php:83-92` исключить запись ПДн в debug-лог (маскировать телефон/имя), как уже сделано для SMTP-учёток.
4. Добавить `.gitignore` с `logs/`, `*.log` (см. F12).

### 🔴 F2. Отсутствует `.htaccess`, заявленный как реализованная мера

`SECURITY_AUDIT.md:15-21` утверждает, что добавлен `.htaccess` с запретом листинга, закрытием `logs/`, `.git/`, `phpmailer/`, backup/test/docs и security-заголовками. **Фактически файла `.htaccess` в репозитории нет** (ни в корне, ни в `public_html/`).

Это значит, что на Apache-хостинге **ни одна из заявленных мер не действует**: каталоги могут листоваться, `logs/` (с ПДн из F1), `.git/`, backup-файлы и `*.md`/`*.txt`/`*.py` доступны напрямую по URL.

**Риск:** прямой доступ к логам с ПДн, исходникам, бэкапам прайс-листов и служебным файлам.

**Рекомендации:**
1. Добавить реальный `.htaccess` (или server-блок Nginx) с описанными в `SECURITY_AUDIT.md` правилами.
2. Привести `SECURITY_AUDIT.md` в соответствие с фактическим состоянием (сейчас он вводит в заблуждение).

### 🟠 F3. Доверие к `X-Forwarded-For` → обход rate-limit

`send-mail.php:96-108`:

```php
$forwarded = $_SERVER['HTTP_X_FORWARDED_FOR'] ?? '';
if ($forwarded) {
    $candidates = array_map('trim', explode(',', $forwarded));
    foreach ($candidates as $candidate) {
        if (filter_var($candidate, FILTER_VALIDATE_IP)) {
            return $candidate;  // берётся клиент-управляемый заголовок
        }
    }
}
```

`X-Forwarded-For` задаётся клиентом и легко подделывается. Так как ключ rate-limit строится из этого IP (`send-mail.php:190`: `rate_limit_ . md5($ip)`), атакующий, меняя заголовок в каждом запросе, **полностью обходит ограничение в 3 запроса/мин** и может спамить форму/SMTP.

**Рекомендации:**
- Доверять `X-Forwarded-For` только если запрос пришёл от известного доверенного прокси/балансировщика; иначе использовать `REMOTE_ADDR`.
- Сделать список доверенных прокси конфигурируемым через `.env`.

### 🟠 F4. Нет CAPTCHA и CSRF-защиты формы

В `send-mail.php:1-9` сам код помечает «Add reCAPTCHA verification before processing» как TODO, но проверки нет. Форма принимает любой POST с корректным JSON и валидным форматом телефона. Отсутствует и CSRF-токен.

**Риск:** автоматический спам заявками, нагрузка на SMTP/Telegram, замусоривание ящика, возможный отказ почтового аккаунта за рассылку.

**Рекомендации:** добавить reCAPTCHA v3 / hCaptcha или honeypot-поле + одноразовый токен формы; серверную проверку капчи до отправки письма.

### 🟠 F5. Тяжёлые ресурсы, отдаваемые в браузер

Крупнейшие файлы (отслеживаются git и/или доступны клиенту):

| Файл | Размер |
|------|--------|
| `prices_list.json` | **12.3 МБ** |
| `prices_materials.json` | **8.4 МБ** |
| `images/flat2.png` | 2.4 МБ |
| `images/Villa_Scandinavian.png` | 2.3 МБ |
| `calc-repair-quest.js` | 1.1 МБ |
| `calc-render.js` | 0.88 МБ |
| `detailed-calc.js` | 0.79 МБ |
| `styles.css` | 0.44 МБ |

Загрузка многомегабайтного JSON и JS блокирует интерактивность калькулятора, особенно на мобильных (вопреки требованию AGENTS.md о мобильной адаптации). Большие PNG не оптимизированы (часть картинок уже в `.webp`, но самые тяжёлые — PNG/JPG).

**Рекомендации:**
1. Перенести расчёт и прайсы на сервер (`/api/...`), как уже рекомендует `SECURITY_AUDIT.md:38-43` — это решает и производительность, и защиту логики.
2. Если данные нужны на клиенте — отдавать с gzip/brotli, дробить на части, грузить лениво.
3. Перегнать тяжёлые PNG/JPG в WebP/AVIF и добавить `loading="lazy"`, responsive `srcset`.

### 🟡 F6. Tailwind через CDN в production

`index.html:52` и `smeta-pro.html:56`:

```html
<script src="https://cdn.tailwindcss.com"></script>
```

`cdn.tailwindcss.com` — это JIT-сборка для прототипирования; она сама выводит предупреждение «should not be used in production», тянет лишний JS и компилирует стили в рантайме, замедляя первую отрисовку, и создаёт зависимость от стороннего CDN.

**Рекомендации:** собрать Tailwind в статический минифицированный CSS (`npx tailwindcss -o styles.tw.css --minify`) и подключать локально. Это также упростит включение строгого CSP (см. F10).

### 🟡 F7. Битые ссылки в SEO-разметке

- `robots.txt` указывает `Sitemap: https://вашимастера.рус/sitemap.xml`, но **`sitemap.xml` в репозитории отсутствует**.
- `index.html:18` задаёт `og:image = .../images/og-image.jpg`, но **`images/og-image.jpg` отсутствует** → при шаринге в соцсети не будет превью.

**Рекомендации:** сгенерировать `sitemap.xml`; добавить `og-image.jpg` 1200×630 (или поправить путь на существующий файл).

### 🟡 F8. Замусоренный репозиторий (≈45 МБ, 170 файлов)

В репозитории лежат артефакты, которым там не место:

- **Бэкапы:** `index_backup.html`, `index_original.html` (по 527 КБ), `prices_list.json.backup`, `prices_list_backup_20260506.json`, `prices_list_fixed.json`.
- **Временные файлы:** `temp_repair_category_fields.txt`, `temp_repair_options.txt`, `temp_repair_section.txt`, `patch_result.txt`, `lint_send_mail.txt`, `lint2_send_mail.txt`.
- **Тестовые страницы в корне:** `test_materials.html`, `test_stairs.html`, `test-mail-fix.php`.
- **Полное дублирование каталога картинок:** `images/` и `public_html/images/` содержат идентичные файлы (`flat2.png` совпадает байт-в-байт) — двойной вес.

**Риск:** раздувание клонов/деплоя, путаница «какой файл актуален», случайная публикация бэкапов и тест-скриптов (особенно при отсутствии `.htaccess`, см. F2).

**Рекомендации:** убрать мусор из репозитория, устранить дублирование каталогов, тестовые страницы вынести в `experiments/`/`tests/`, добавить `.gitignore`.

### 🟡 F9. Неатомарный файловый rate-limit

`send-mail.php:197-219` читает файл, фильтрует таймстемпы и затем перезаписывает его отдельной операцией. Между чтением и записью нет общей блокировки (`LOCK_EX` стоит только на записи) — при параллельных запросах возможен **TOCTOU-гонка** и потеря отметок. Плюс хранение по файлу на IP плохо масштабируется и легко обходится при смене IP/заголовка (F3).

**Рекомендации:** использовать атомарное хранилище (Redis `INCR`+`EXPIRE` или БД) с серверным ключом по доверенному IP.

---

### 🟢 F10. Inline-обработчики блокируют строгий CSP

В `index.html` 52 инлайновых обработчика (`onclick`/`onchange`/`oninput`/…). Это подтверждает `SECURITY_AUDIT.md:34`: строгий CSP невозможно включить, пока они есть. Без CSP сложнее защититься от потенциального XSS.

**Рекомендации:** вынести обработчики в адресные `addEventListener`, затем включить `Content-Security-Policy` с запретом `unsafe-inline`.

---

### 🟢 F11. Информативные сообщения об ошибках SMTP

`send-mail.php` возвращает клиенту детализированные статусы: `'Invalid username'`, `'Authentication failed...'`, `'Server error: ' . $response` (строки 375, 388, 333). Это раскрывает внутреннюю механику и состояние почтового сервера.

**Рекомендации:** наружу отдавать обобщённое «Не удалось отправить заявку, попробуйте позже», детали писать только в защищённый лог.

---

### 🟢 F12. Нет `.gitignore` и `.env.example`

В репозитории отсутствует `.gitignore`. Это и стало причиной попадания `mail_debug.log` (F1) и бэкапов (F8) в историю. Также нет `.env.example` — притом что `send-mail.php:34-67` критически зависит от `.env` (SMTP/Telegram), и новому разработчику неочевидно, какие ключи нужны.

**Рекомендации:** добавить `.gitignore` (`.env`, `logs/`, `*.log`, `*.backup`, `*_backup*`, `temp_*`) и `.env.example` с перечнем требуемых переменных без значений.

## 4. Сильные стороны (для баланса)

- **SEO-база добротная:** заполнены `description`/`keywords`, Open Graph, Twitter Card, canonical, geo-теги; `lang="ru"`; все 7 `<img>` в `index.html` имеют `alt`.
- **`send-mail.php` уже неплохо укреплён:** валидация телефона по строгому regex, `htmlspecialchars(ENT_QUOTES)` на всех полях, CORS-allowlist вместо отражения `Origin` (строки 122-133), статические заголовки письма (низкий риск header-injection), маскирование SMTP-учёток в логах, `display_errors=0`.
- **Секреты вынесены в `.env`** и не закоммичены (в репозитории нет `.env` и захардкоженных паролей).
- **Защита от AI-скрейперов** в `robots.txt` (GPTBot, ClaudeBot, CCBot и др.).
- **Архитектура фронтенда задокументирована** (`README.md`, `ARCHITECTURE.md`), крупный код вынесен из HTML в модули.

## 5. Приоритетный план действий

**Сделать немедленно (критично):**
1. Удалить `mail_debug.log` из репозитория и истории git; вынести `logs/` из веб-корня (F1).
2. Добавить реальный `.htaccess`/конфиг Nginx с заявленными правилами (F2).
3. Добавить `.gitignore`, чтобы утечка не повторилась (F12).

**Ближайший спринт (высокая критичность):**
4. Исправить доверие к `X-Forwarded-For` (F3).
5. Подключить CAPTCHA + CSRF к форме (F4).
6. Спланировать перенос расчётов/прайсов на сервер — закрывает F5 и часть рисков защиты логики.

**Среднесрочно:**
7. Собрать Tailwind локально (F6); создать `sitemap.xml` и `og-image.jpg` (F7).
8. Вычистить репозиторий и устранить дубликаты `images/` (F8).
9. Перевести rate-limit на Redis/БД (F9).

**По мере рефакторинга:**
10. Убрать inline-обработчики и включить CSP (F10); обобщить сообщения об ошибках (F11).
