## Архитектура проекта (кратко)

Этот репозиторий — статическая витрина на `index.html` + PHP-обработчик отправки заявок (`send-mail.php` через PHPMailer). Основная сложность во фронтенде — большой детализированный калькулятор с большим количеством UI-логики и расчетов.

Ключевая договоренность текущей архитектуры: **все модули подключаются как обычные `<script>` (не ES-модули)** и работают через **глобальные функции/переменные**. Поэтому **порядок подключения критичен**.

---

## Точки входа

- **`index.html`**: единственная страница, подключает CSS/JS.
- **`styles.css`**: вынесенные стили из `index.html`.
- **`ui-core.js`**: UI для страницы (модалки, меню, прокрутка, формы и т.д.).
- **`simple-calc.js`**: простой калькулятор (площадь/тип).
- **`send-mail.php`**: прием формы и отправка письма.

---

## Модули детализированного калькулятора

Ниже — текущая логическая разбивка. Названия модулей отражают “зону ответственности”, но технически это **все еще общий глобальный неймспейс**.

### Глобальное состояние

- **`calc-core.js`**
  - Глобальные переменные состояния: `priceData`, `roomData`, `selectedItems`, `itemQuantities`, `repairQuestState` и т.п.
  - `syncAppStateToNamespace()` — синхронизация в `window.App.state`.

### Базовые утилиты / доп. ветки

- **`calc-utils.js`**: утилиты и проверки заполненности данных секций (в т.ч. для demolition/repair веток).
- **`demolition.js`**: логика демонтажных разделов (рендер полей, хранение в `roomData.demolitionData`, “готово/не готово”).

### Детализированный калькулятор (UI + расчеты)

- **`calc-init.js`**
  - Загрузка `prices.json`, инициализация `roomData`, старт `initDetailedCalculator()`.
  - Общие “контейнерные” переключатели секций и базовые функции, от которых зависит остальной UI.
- **`calc-render.js`**
  - Рендер специфических блоков/подблоков по помещениям (двери/окна/балконы и т.п.), хелперы ввода.
- **`calc-repair-quest.js`**
  - “Квест” (опрос): сбор ответов, UI шагов, аудит, применение результатов в состояние калькулятора.
- **`calc-building.js`**
  - Логика выпадающих списков по зданию (тип/подтип/материал/этажность и пр.).
- **`calc-ui-toggles.js`**
  - Небольшие UI-переключатели опций (вкл/выкл блоков).
- **`calc-address.js`**
  - Автоподсказки адреса и выбор адреса.
- **`calc-room-ui.js`**
  - Управление карточками/группами помещений и их поведением (свернуть/развернуть, изменения значений и т.п.).
- **`calc-summary-render.js`**
  - Рендер секций работ/материалов/допуслуг и промежуточных итогов.
- **`calc-pricing.js`**
  - Выбор позиций, изменение количества, поиск прайсовых элементов, пересчеты и обновление отображения.
- **`calc-flow.js`**
  - Оставшаяся “сценарная”/связующая логика, которая дергает остальные блоки.

## Порядок подключения скриптов (обязательный)

Ниже порядок, который должен оставаться корректным (как минимум в пределах группы “детализированный калькулятор”):

1. `simple-calc.js`
2. `ui-core.js`
3. `calc-core.js`
4. `calc-utils.js`
5. `demolition.js`
6. `calc-init.js`
7. `calc-render.js`
8. `calc-repair-quest.js`
9. `calc-building.js`
10. `calc-ui-toggles.js`
11. `calc-address.js`
12. `calc-room-ui.js`
13. `calc-summary-render.js`
14. `calc-pricing.js`
15. `calc-flow.js`

Если менять порядок — есть высокий риск, что часть функций окажется “не определена” в момент вызова (так как это не ES-модули и не бандл).

---

## Правила безопасного рефакторинга

- **Перенос 1-в-1 сначала**: сначала вынос кода без функциональных изменений, только после этого — улучшения.
- **Проверять глобальные зависимости**: любые функции, вызываемые из HTML-атрибутов (`onclick`, `onchange`, `oninput`), должны оставаться в глобальной области видимости.
- **Не ломать API состояния**: структура `roomData`, `selectedItems`, `itemQuantities`, `repairQuestState` должна оставаться совместимой.
- **Дробить по “срезам”**:
  - сначала выделять крупный участок в новый файл и подключать,
  - потом уже внутри файла улучшать (именование, повтор, небольшие чистые функции).
- **Фиксировать точки входа**:
  - `loadPrices()` и `initDetailedCalculator()` — ключевые стартовые функции;
  - все “render/update” должны работать после загрузки `prices.json`.

## Следующие улучшения (опционально)

Если потребуется дальнейшая модернизация (не обязательна прямо сейчас):
- перейти с inline-обработчиков на `addEventListener` (с поэтапной совместимостью),
- собрать JS в бандл (Vite/Rollup) и уйти от глобального неймспейса,
- выделить слой “чистых расчетов” без DOM (чтобы проще тестировать).

## Backend-ready слой

Начат постепенный вынос “мозга” калькулятора из публичного JS:

- **`backend/api/coverings.php`** — первый API endpoint для backend-controlled каталогов покрытий.
- **`backend/api/covering-autofill.php`** — первый API endpoint для backend-controlled автозаполнения паспорта покрытия.
- **`backend/api/covering-validate.php`** — первый API endpoint для backend-controlled проверки обязательных полей паспорта покрытия.
- **`backend/api/covering-options.php`** — первый API endpoint для backend-controlled совместимости вариантов покрытия, контекстных обязательных групп и прогресса заполнения паспорта.
- **`backend/lib/covering-floor.php`** — общий backend-модуль пола: распознавание покрытия, выбранного формата, совместимых опций и контекстных обязательных групп.
- **`backend/data/coverings/...`** — закрытые данные каталогов и совместимости. Сейчас там живут `walls.decorative_plaster` и первый каталог пола `floors.common`. На Apache прямой доступ закрывает `backend/data/.htaccess`; для Nginx/другого сервера нужно отдельно запретить публичную отдачу `backend/data`.
- **`repair-coverings-api.js`** — тонкий frontend-клиент, который будет получать каталоги через API без изменения текущей глобальной архитектуры скриптов.
- **`contracts/covering-catalog.contract.json`** — контракт данных каталога покрытия.
- **`assets/repair-coverings/...`** — публичные изображения/превью покрытий. Сюда кладутся только собственные, лицензированные или разрешенные изображения.

Правило миграции: frontend показывает интерфейс и временно может иметь fallback-логику, но каталоги совместимости, автоподбор, валидацию, цены, коэффициенты и расчет постепенно переносим в `backend/api`.
